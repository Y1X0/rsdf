- [ ] Items 1, 2, 3, 4, 5, and 8 are each independently verified `READY` — not just configured, *verified*: a real credential/connection is confirmed to actually work (a real API call succeeds, a real DB connection/restore succeeds), with the evidence recorded in this table, not just present in an env var.
- [ ] Item 6 (human reviewer) is `READY` only with all three of: a real reviewer name, confirmation they've accepted the role, and confirmation they understand the `reason_code` requirement (`docs/PILOT_PLAN.md` §1.3) — recorded in the Verification Evidence column, not assumed.
- [ ] Item 7 is `READY` to at least its minimum bar: one real account exists and a manual-vs-automated publishing decision has been made and documented for it.
- [ ] Every `Owner` field above names a real, real assignee for the item's resolution — currently every row correctly says `Project owner` because every remaining gap requires an action only the project owner (or their team) can take; this is accurate, not a placeholder to be embarrassed about.
- [ ] This document has been re-checked and its `Date Checked` column updated immediately before day one — a status set days or weeks earlier is not sufficient, since credentials/accounts can regress (a key revoked, an account flagged) between when a row was last verified and when the pilot actually starts.
